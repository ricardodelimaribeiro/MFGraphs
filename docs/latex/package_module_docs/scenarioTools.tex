\section{High-level explanation}

\texttt{scenarioTools.wl} is the typed scenario kernel of the active MFGraphs architecture. It converts raw network-and-parameter input into a validated, completed, and cached \texttt{scenario[<|\ldots|>]} object. This is the module that establishes the contract for what a scenario is, what data it must contain, how topology is derived, and which defaults are filled automatically.

Architecturally, this file is where MFGraphs stops being a loose set of associations and becomes a disciplined object pipeline. It performs model normalization, validation, switching-cost completion and closure, Hamiltonian normalization, topology construction, and default completion. Downstream modules therefore assume that a scenario already contains a consistent \texttt{"Model"}, a normalized \texttt{"Hamiltonian"}, and cached \texttt{"Topology"} data.

\section{Scenario schema}

A completed \texttt{scenario[\textellipsis]} wraps an association with the following top-level keys.

\begin{center}
\renewcommand{\arraystretch}{1.2}
\begin{longtable}{@{}p{3.6cm} p{10.9cm}@{}}
\toprule
\textbf{Key} & \textbf{Contents} \\
\midrule
\endhead
\texttt{"Model"} & The network description: \texttt{"Vertices"}, \texttt{"Adjacency"} (or \texttt{"Graph"}), \texttt{"Entries"} (vertex/inflow pairs), \texttt{"Exits"} (vertex/exit-cost pairs), \texttt{"Switching"} (cost rows or an association keyed by transition triples), and optionally \texttt{"EdgeEntryTolls"}. After completion \texttt{"Switching"} holds a cost for every admissible transition. \\
\texttt{"Hamiltonian"} & Normalized Hamiltonian parameters: \texttt{"Alpha"}, \texttt{"V"}, \texttt{"G"}, plus the edge-keyed override maps \texttt{"EdgeAlpha"}, \texttt{"EdgeV"}, \texttt{"EdgeG"}. \\
\texttt{"Topology"} & Cached auxiliary-graph data produced by \texttt{buildAuxiliaryTopology}: the undirected base graph, auxiliary entry/exit vertices, augmented graph, directed auxiliary pairs, and admissible transition triples. \\
\texttt{"InputProvenance"} & The boundary, switching, toll and Hamiltonian input exactly as given, kept before any normalization so exactness checks can see inexact input. \\
\texttt{"Identity"} & Optional identifying metadata (name, source). \\
\texttt{"Benchmark"} & Benchmark-related fields, filled with defaults by \texttt{completeScenario}. \\
\bottomrule
\end{longtable}
\end{center}

The \texttt{"Topology"} block is computed once inside \texttt{makeScenario} and is the reason every downstream stage runs in time proportional to its own work rather than re-walking the graph.

\subsection*{Auxiliary vertices}

Each entry vertex $v$ gets an auxiliary vertex \texttt{auxEntry[v]} and each exit vertex $v$ gets \texttt{auxExit[v]}. Boundary inflow runs along $\{\texttt{auxEntry[v]}, v\}$ and boundary outflow along $\{v, \texttt{auxExit[v]}\}$, so these labels appear in flow and value variables such as \texttt{j[auxEntry[1], 1]} and \texttt{u[auxExit[3], 3]}. The heads are protected, inert symbols: code identifies an auxiliary vertex by pattern (\texttt{\_auxEntry}, \texttt{\_auxExit}) or by the topology's \texttt{"AuxEntryVertices"} and \texttt{"AuxExitVertices"} lists, never by parsing a name.

\subsection*{Switching costs}

A switching cost $c(r,v,w)$ is the cost of moving at junction $v$ from edge $(r,v)$ onto edge $(v,w)$. Only admissible transitions may carry costs: $\{r,v\}$ and $\{v,w\}$ must be edges and $r \neq w$. A cost is a nonnegative number, \texttt{Infinity} (a blocked transition), or a pure function of the transition flow.

Completion gives every admissible transition a cost: the explicit cost, otherwise the expanded edge entry toll, otherwise $0$. The finite costs at each junction are then replaced by their metric closure, the cheapest sequence of switches, so that
\[
  c(r,v,w) \le c(r,v,k) + c(k,v,w)
\]
holds among them. The closure is an exact Floyd--Warshall computation, so rational costs stay rational. Blocked transitions and pure-function costs are neither changed by the closure nor used as intermediate steps.

\section{Low-level explanation of functions and functionality}

\subsection*{\texttt{scenario}}

\texttt{scenario[assoc]} is the typed wrapper head for scenario objects. Its meaning comes from the convention that the wrapped value is an association with the keys listed above. Users normally do not construct \texttt{scenario} objects by hand; the supported path is \texttt{makeScenario}, which guarantees validation and completion.

\subsection*{\texttt{scenarioQ}}

\texttt{scenarioQ[x]} returns \texttt{True} exactly when \texttt{x} matches the typed scenario wrapper pattern \texttt{scenario[\_Association]}. It is the basic predicate used throughout the package to guard scenario-only entrypoints.

\subsection*{\texttt{auxEntry} and \texttt{auxExit}}

\texttt{auxEntry[v]} and \texttt{auxExit[v]} label the auxiliary entry and exit vertices attached to boundary vertex \texttt{v}. They have no definitions and are \texttt{Protected}, so a notebook assignment cannot redefine them.

\subsection*{\texttt{makeScenario}}

\texttt{makeScenario[assoc]} is the module's main constructor. It records the input provenance, fills \texttt{"Vertices"} and \texttt{"Adjacency"} from a \texttt{"Graph"} when needed, validates the input, builds the auxiliary topology, and calls \texttt{completeScenario}. It returns the first problem found as \texttt{Failure["ScenarioValidation", \ldots]} without issuing messages.

\begin{verbatim}
s = makeScenario[<|
  "Model" -> <|
    "Vertices" -> {1,2,3},
    "Adjacency" -> {{0,1,0},{0,0,1},{0,0,0}},
    "Entries" -> {{1,10}},
    "Exits" -> {{3,0}},
    "Switching" -> {}
  |>
|>];
\end{verbatim}

Validation rejects:
\begin{itemize}
\item a missing or non-association \texttt{"Model"}, missing required model keys (\texttt{"Switching"} may be omitted when \texttt{"EdgeEntryTolls"} is given), the retired \texttt{"Data"} key, and the old key name \texttt{"edgeEntryTolls"};
\item \texttt{"Vertices"} that are not distinct integers, or that are not vertices of a given \texttt{"Graph"};
\item an \texttt{"Adjacency"} that is not a square numeric matrix with one row per vertex, or that has self-loops;
\item boundary values that are not real, negative inflows, boundary vertices outside \texttt{"Vertices"}, a vertex listed twice in \texttt{"Entries"} or twice in \texttt{"Exits"}, and a vertex that is both an entry and an exit;
\item switching costs that are negative or of the wrong form, and switching keys that are not admissible transitions;
\item tolls on pairs that are not edges;
\item a \texttt{"Hamiltonian"} that is not an association, has keys other than the six listed above, or has invalid defaults or edge overrides.
\end{itemize}

\subsection*{\texttt{validateScenario}}

\texttt{validateScenario[s]} returns \texttt{True} when \texttt{s} is a scenario object that passes every check \texttt{makeScenario} applies, and \texttt{False} otherwise. On \texttt{False} it issues \texttt{validateScenario::invalid} naming the first problem, or \texttt{validateScenario::notscenario} for input that is not a scenario. It uses the cached topology when the scenario has one, so a completed scenario validates.

\subsection*{\texttt{completeScenario}}

\texttt{completeScenario[s]} fills in defaults: absent Hamiltonian values, benchmark defaults, and a complete, closed switching-cost association over every admissible transition. If the scenario has no cached topology, it issues \texttt{completeScenario::notopology}, rebuilds the topology, and stores it in the result. It does not validate; call \texttt{validateScenario} first. Completing an already completed scenario returns it unchanged.

\subsection*{\texttt{scenarioData}}

\texttt{scenarioData[s]} returns the underlying association, while \texttt{scenarioData[s,key]} performs key lookup with \texttt{Missing["KeyAbsent", key]} fallback. It is the standard read interface for every downstream module.

\subsection*{\texttt{buildAuxiliaryTopology}}

\texttt{buildAuxiliaryTopology[model]} constructs the cached topology block: the undirected base network, the auxiliary entry and exit vertices and edges, the augmented graph, the directed pair lists (\texttt{"AuxPairs"}), and the admissible transition triples (\texttt{"AuxTriples"}). It returns \texttt{\$Failed} when the model's vertices, adjacency, entries, or exits are malformed.

\subsection*{Private helpers}

\begin{itemize}
\item \texttt{scenarioInputProblem}, \texttt{hamiltonianProblem}, \texttt{switchingProblem} and \texttt{checkedTopology} implement validation; each returns a \texttt{ScenarioValidation} failure for the first problem found.
\item \texttt{normalizeScenarioModel} and \texttt{buildAdjacencyFromGraph} derive \texttt{"Vertices"} and \texttt{"Adjacency"} from a \texttt{"Graph"}; a model that does not match its graph is left unchanged for validation to report.
\item \texttt{normalizeSwitchingCosts} and \texttt{normalizeHamiltonianSpec} put switching costs and Hamiltonian specs into canonical association form.
\item \texttt{expandEdgeEntryTolls} turns a toll on entering edge $\{v,w\}$ at $v$ into the costs $c(r,v,w)$ for every other neighbour $r$ of $v$; numeric tolls become constant functions of the flow.
\item \texttt{completedSwitchingCosts}, \texttt{metricClosureSwitchingCosts} and \texttt{junctionClosure} complete and close the switching costs as described above.
\item \texttt{auxTriplesFromPairs} enumerates admissible transitions from directed pairs, and \texttt{undirectedAdjacency} symmetrizes an adjacency matrix.
\end{itemize}

\section{Usage guidance}

Users should think of this file as the package's gatekeeper. Any raw network or graph should enter the active MFGraphs workflow through \texttt{makeScenario}. Advanced users may inspect \texttt{scenarioData} and the topology, but bypassing the constructor means taking responsibility for normalization and validation manually; \texttt{validateScenario} checks a hand-built scenario against the same rules.
